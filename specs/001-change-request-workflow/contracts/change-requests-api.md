# قرارداد HTTP API درخواست‌های تغییر

همهٔ عملیات به هدر `Authorization: Bearer <token>` نیاز دارند. بدنهٔ درخواست و پاسخ، در صورت وجود، JSON است.

## مسیرها

| روش و مسیر                                   | ورودی                                                          | نتیجهٔ موفق                                                      |
| -------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------- |
| `POST /change-requests`                      | `title`، `description` و `reason`                              | `201` و درخواست ساخته‌شده با وضعیت `Draft` و نسخهٔ ۱             |
| `GET /change-requests`                       | بدون بدنه                                                      | `200` و فهرست درخواست‌هایی که کاربر اجازهٔ مشاهدهٔ آن‌ها را دارد |
| `GET /change-requests/{id}`                  | شناسهٔ درخواست در مسیر                                         | `200` و اطلاعات همان درخواست در صورت داشتن دسترسی                |
| `PATCH /change-requests/{id}`                | حداقل یکی از `title`، `description` و `reason` همراه `version` | `200` و درخواست ویرایش‌شده با نسخهٔ جدید. وضعیت ثابت می‌ماند     |
| `POST /change-requests/{id}/submit`          | `version`                                                      | `200` و درخواست در وضعیت `PendingReview` با نسخهٔ جدید           |
| `POST /change-requests/{id}/approve`         | `version`                                                      | `200` و درخواست در وضعیت `Approved` با نسخهٔ جدید                |
| `POST /change-requests/{id}/request-changes` | `version`                                                      | `200` و درخواست در وضعیت `ChangesRequested` با نسخهٔ جدید        |

## قواعد ورودی و دسترسی

- عنوان، شرح و دلیل در زمان ثبت اجباری‌اند و باید متن غیرخالی باشند. در ویرایش، همین قاعده برای فیلدهای ارسال‌شده برقرار است.
- ویرایش و ارسال فقط توسط ثبت‌کنندهٔ همان درخواست با نقش Requester، در وضعیت `Draft` یا `ChangesRequested` مجاز است.
- تأیید و بازگرداندن برای اصلاح فقط در وضعیت `PendingReview` و توسط Reviewer مجازی انجام می‌شود که ثبت‌کنندهٔ همان درخواست نیست.
- فیلد `version` در ویرایش و تغییر وضعیت اجباری است و باید عدد صحیح مثبت باشد. کاربر آن را از آخرین پاسخ مربوط به همان درخواست می‌گیرد.
- درخواست‌کنندهٔ دارای نقش Requester، درخواست‌های خودش را می‌بیند. Reviewer می‌تواند درخواست‌های `PendingReview` را ببیند. اگر کاربر هر دو نقش را داشته باشد، دسترسی مشاهدهٔ هر دو نقش را دارد.

## نمونهٔ پاسخ ثبت موفق

```json
{
  "id": 12,
  "title": "اصلاح گزارش خروجی",
  "description": "ستون وضعیت به گزارش اضافه شود",
  "reason": "پیگیری درخواست‌ها ساده‌تر شود",
  "requesterId": 3,
  "status": "Draft",
  "version": 1
}
```

## خطاها

| کد HTTP | کد خطا             | شرایط                                         |
| ------- | ------------------ | --------------------------------------------- |
| `400`   | `INVALID_INPUT`    | ورودی ناقص یا نامعتبر است                     |
| `401`   | `UNAUTHENTICATED`  | توکن ارسال نشده یا نامعتبر است                |
| `403`   | `FORBIDDEN`        | کاربر مجوز عملیات یا مشاهدهٔ درخواست را ندارد |
| `404`   | `NOT_FOUND`        | درخواست با شناسهٔ داده‌شده وجود ندارد         |
| `409`   | `INVALID_STATE`    | وضعیت فعلی درخواست اجازهٔ عملیات را نمی‌دهد   |
| `409`   | `VERSION_CONFLICT` | نسخهٔ ارسالی با نسخهٔ فعلی درخواست برابر نیست |

در عملیات روی یک درخواست موجود، پس از اعتبارسنجی ورودی و شناسایی کاربر، سرور وجود درخواست و سپس مجوز کاربر را بررسی می‌کند. برای کاربر مجاز، نسخه پیش از وضعیت بررسی می‌شود. مثلاً ارسال دوباره با نسخهٔ قدیمی خطای `VERSION_CONFLICT` دارد. ارسال دوباره با نسخهٔ فعلی در وضعیت `PendingReview` خطای `INVALID_STATE` دارد.

نمونهٔ خطای نسخهٔ قدیمی:

```json
{
  "code": "VERSION_CONFLICT",
  "message": "درخواست تغییر کرده است. آن را دوباره بخوانید."
}
```
