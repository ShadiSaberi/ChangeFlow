# تسک‌های گردش درخواست تغییر

## آماده‌سازی پروژه

- [x] T001 — پروژه Node.js را با npm راه‌اندازی کن و دستورهای اجرای API و آزمون‌ها را در `package.json` تعریف کن.
- [x] T002 — اتصال به SQLite و اسکریپت ساخت جدول‌ها را طبق `data-model.md` آماده کن؛ از جمله `change_requests.id`، `change_requests.title`، `change_requests.description`، `change_requests.reason`، `change_requests.requester_id`، `change_requests.status` و `change_requests.version` و قیود آن‌ها. قید یکتایی `user_roles` باید روی زوج (`user_roles.user_id`, `user_roles.role`) اعمال شود و `access_tokens.token_hash` به‌تنهایی باید یکتا باشد. پیش‌نیاز: T001.
- [x] T003 — کاربران آزمایشی، نقش‌ها و اطلاعات اعتبارسنجی توکن را در دیتابیس آماده کن؛ فیلدهای `users.id`، `users.name`، `user_roles.user_id`، `user_roles.role`، `access_tokens.token_hash` و `access_tokens.user_id` و قیدهای نقش و یکتایی ترکیبی را طبق `data-model.md` بساز. پیش‌نیاز: T002.

## شناسایی کاربر و ثبت پیش‌نویس

- [x] T004 — توکن ارسالی را بررسی کن و شناسهٔ کاربر را به دست بیاور. نقش‌های فعلی کاربر را از SQLite بخوان. پیش‌نیاز: T003. مرتبط با FR-06.
- [x] T005 — مسیر `POST /change-requests` را بساز. `change_requests.title`، `change_requests.description` و `change_requests.reason` را به‌صورت متن غیرخالی اعتبارسنجی کن، مجوز `Requester` را بررسی کن و درخواست را با `change_requests.requester_id` گرفته‌شده از کاربر احراز هویت‌شده، `change_requests.status` برابر `Draft` و `change_requests.version` برابر ۱ ذخیره کن؛ مطابق قیدهای `data-model.md`. پیش‌نیاز: T004. مرتبط با FR-01 و CL-07.
- [x] T006 — برای ثبت موفق پیش‌نویس تست خودکار بنویس. بررسی کن پاسخ `201` برگردد و درخواست در دیتابیس با شناسهٔ همان کاربر و وضعیت `Draft` ذخیره شود. پیش‌نیاز: T005. مرتبط با FR-01.

## مشاهده، ویرایش و ارسال درخواست

- [x] T007 — مسیرهای `GET /change-requests` و `GET /change-requests/{id}` را بساز. هر کاربر فقط درخواست‌هایی را ببیند که طبق CL-02 اجازهٔ مشاهدهٔ آن‌ها را دارد. شمارهٔ `change_requests.version` را هم در پاسخ برگردان. پیش‌نیاز: T004. مرتبط با CL-02.
- [x] T008 — برای ویرایش و تغییر وضعیت، یک تراکنش SQLite آماده کن. داخل همان تراکنش، نقش فعلی کاربر و اطلاعات درخواست را بخوان و `change_requests.requester_id`، `change_requests.status` و `change_requests.version` را طبق قواعد عملیات بررسی کن. اگر همهٔ شرط‌ها برقرار بودند، تغییر را فقط در صورت برابری نسخهٔ ارسالی و نسخهٔ ذخیره‌شده ثبت کن و `change_requests.version` را در همان به‌روزرسانی یک واحد افزایش بده؛ مقادیر مجاز `change_requests.status` و قیدهای مدل در `data-model.md` مرجع‌اند. تسک‌های T009، T010، T012 و T013 از این سازوکار استفاده کنند. پیش‌نیاز: T002. مرتبط با FR-04، FR-06، FR-07 و CL-03.
- [x] T009 — مسیر `PATCH /change-requests/{id}` را برای ویرایش بساز. فقط ثبت‌کننده با نقش Requester بتواند `change_requests.title`، `change_requests.description` یا `change_requests.reason` را در درخواست خودش، در وضعیت `Draft` یا `ChangesRequested` ویرایش کند؛ هر فیلد ارسالی باید متن غیرخالی باشد. ویرایش موفق `change_requests.status` را تغییر نمی‌دهد و طبق `data-model.md` نسخه را افزایش می‌دهد. پیش‌نیاز: T004 و T008. مرتبط با FR-02، FR-05، FR-07 و CL-07.
- [x] T010 — مسیر `POST /change-requests/{id}/submit` را بساز. پس از بررسی هویت، مجوز فعلی، مالکیت و نسخه، درخواست را از `Draft` یا `ChangesRequested` به `PendingReview` ببر. پیش‌نیاز: T004 و T008. مرتبط با FR-02، FR-06، FR-07 و CL-04.
- [x] T011 — ارسال موفق پیش‌نویس را تست کن. بررسی کن API پاسخ `200` بدهد و وضعیت همان درخواست در دیتابیس `PendingReview` شود. پیش‌نیاز: T005 و T010. مرتبط با FR-02.

## تأیید و بازگرداندن درخواست برای اصلاح

- [x] T012 — مسیر `POST /change-requests/{id}/approve` را بساز. اگر کاربر در زمان اقدام نقش Reviewer دارد، ثبت‌کنندهٔ درخواست نیست، نسخه درست است و درخواست در وضعیت `PendingReview` قرار دارد، وضعیت را به `Approved` تغییر بده. پیش‌نیاز: T004 و T008. مرتبط با FR-03، FR-04، FR-06 و FR-07.
- [x] T013 — مسیر `POST /change-requests/{id}/request-changes` را بساز. با همان بررسی‌های مجوز، مالکیت، نسخه و وضعیت، درخواست را به `ChangesRequested` ببر. پیش‌نیاز: T004 و T008. مرتبط با FR-03، FR-04، FR-06، FR-07 و CL-06.
- [x] T014 — تأیید موفق توسط بررسی‌کنندهٔ مجاز و مستقل را تست کن. پاسخ `200` و وضعیت ذخیره‌شدهٔ `Approved` را بررسی کن. پیش‌نیاز: T005، T010 و T012. مرتبط با FR-03.
- [x] T015 — تلاش ثبت‌کننده‌ای را که نقش Reviewer هم دارد برای تأیید یا بازگرداندن درخواست خودش، در دو آزمون جدا بررسی کن. در هر دو، پاسخ باید `403` باشد و وضعیت ذخیره‌شده `PendingReview` بماند. پیش‌نیاز: T005، T010، T012 و T013. مرتبط با FR-04 و CL-06.


## آزمون‌های باقی‌مانده

- [ ] T020 — برای مسیر ثبت درخواست، پاسخ‌های `400 INVALID_INPUT`، `401 UNAUTHENTICATED` و `403 FORBIDDEN` را با آزمون HTTP بررسی کن و ثابت کن درخواست نامعتبر یا غیرمجاز در SQLite ذخیره نمی‌شود. مرتبط با FR-01، FR-06 و CL-07.
- [ ] T021 — برای `GET /change-requests/{id}` شناسهٔ نامعتبر و درخواست ناموجود را با آزمون HTTP بررسی کن؛ پاسخ‌های `400 INVALID_INPUT` و `404 NOT_FOUND` را طبق جدول خطاهای قرارداد API تأیید کن و قواعد مشاهدهٔ CL-02 را نیز پوشش بده: کاربر مجاز (ثبت‌کننده یا Reviewer برای `PendingReview`) پاسخ موفق بگیرد و کاربر فاقد دسترسی `403 FORBIDDEN` دریافت کند. مرتبط با CL-02 و قرارداد API (خطاهای HTTP).

- [x] T016 — با نقش Requester و شمارهٔ نسخهٔ فعلی، برای ویرایش درخواست تأییدشدهٔ خود اقدام کن. بررسی کن پاسخ `409` با کد `INVALID_STATE` برگردد و محتوا، وضعیت `Approved` و شمارهٔ نسخه در دیتابیس ثابت بمانند. پیش‌نیاز: T005، T009، T010 و T012. مرتبط با FR-05.
- [x] T017 — یک پیش‌نویس را با نسخهٔ ۱ ویرایش کن و بعد دوباره با همان نسخهٔ ۱ تغییر بفرست. بررسی کن پاسخ دوم `409` با کد `VERSION_CONFLICT` باشد و دیتابیس محتوای ویرایش اول و نسخهٔ ۲ را حفظ کند. پیش‌نیاز: T005 و T009. مرتبط با FR-07.
- [x] T018 — درخواست را برای اصلاح برگردان. بررسی کن ثبت‌کننده بتواند محتوای آن را اصلاح کند، وضعیت بعد از ویرایش `ChangesRequested` بماند و بعد از ارسال دوباره به `PendingReview` برسد. پیش‌نیاز: T005، T009، T010 و T013. مرتبط با FR-02 و FR-03.
- [x] T019 — درخواست را با دسترسی Reviewer مشاهده کن، نقش Reviewer را لغو کن و سپس با همان توکن و نسخهٔ فعلی برای تأیید اقدام کن. بررسی کن پاسخ `403` برگردد و وضعیت ذخیره‌شده `PendingReview` بماند. پیش‌نیاز: T005، T007، T010 و T012. مرتبط با FR-06 و CL-03.
