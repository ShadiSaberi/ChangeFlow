# بررسی تصمیم‌های فنی ChangeFlow

## ذخیره‌سازی درخواست‌ها

برای نسخهٔ اول SQLite را انتخاب می‌کنیم. داده‌ها پس از بستن برنامه باقی می‌مانند و برای اجرای محلی API به سرور جداگانهٔ دیتابیس نیاز نداریم.

یک فایل JSON هم می‌تواند داده‌ها را نگه دارد، اما باید خودمان مراقب باشیم که ذخیره‌های هم‌زمان تغییرات یکدیگر را بازنویسی نکنند. SQLite امکان به‌روزرسانی شرطی را می‌دهد. یعنی می‌توانیم تغییر را فقط وقتی ذخیره کنیم که نسخهٔ درخواست هنوز همان نسخه‌ای باشد که کاربر خوانده است.

## شناسایی کاربر و مجوز

**گزینهٔ انتخابی:** توکن آزمایشی برای شناسایی کاربر و خواندن نقش فعلی از SQLite برای بررسی مجوز. این روش به ما اجازه می‌دهد چند کاربر با نقش‌های متفاوت داشته باشیم و لغو نقش Reviewer را بدون ساخت سامانهٔ ورود کامل آزمایش کنیم.

**گزینهٔ دیگر:** استفاده از JWT حاوی نقش کاربر. اگر نقش داخل توکن ملاک تصمیم باشد، ممکن است بعد از لغو نقش، توکن قبلی هنوز آن نقش را نشان دهد. برای رعایت CL-03 باید نقش فعلی را جداگانه بررسی کنیم یا سازوکار ابطال مناسب داشته باشیم.

**محدودیت انتخاب:** توکن‌های این نسخه برای اجرای محلی و آزمون تمرین هستند. مدیریت کامل حساب و ورود سازمانی در محدودهٔ نسخهٔ اول قرار ندارند.

## کنترل تغییرات هم‌زمان

**گزینهٔ انتخابی:** کنترل خوش‌بینانه با شمارهٔ نسخه. کاربر شمارهٔ نسخه‌ای را که خوانده می‌فرستد و SQLite هنگام به‌روزرسانی آن را بررسی می‌کند. اگر داده در فاصلهٔ خواندن تا ذخیره تغییر کرده باشد، درخواست قدیمی رد می‌شود.

**گزینهٔ دیگر:** قفل کردن درخواست از لحظهٔ باز شدن تا پایان ویرایش. این روش می‌تواند کاربران دیگر را منتظر نگه دارد و به مدیریت زمان انقضا و آزاد کردن قفل نیاز دارد.

**دلیل انتخاب:** کاربر می‌تواند درخواست را باز کند و بدون قفل طولانی روی آن کار کند. در عوض، اگر درخواست تغییر کرده باشد، باید دادهٔ تازه را بخواند و تغییرش را دوباره بررسی کند.
