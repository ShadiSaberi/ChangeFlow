# طرح فنی ChangeFlow

## فناوری پروژه

نسخهٔ اول را با JavaScript روی Node.js 20.18.0 به‌صورت یک HTTP API می‌سازیم. برای مدیریت وابستگی‌ها از npm 10.8.2 استفاده می‌کنیم.

دلیل انتخاب: Node.js و npm روی سیستم آماده‌اند و برای ساخت API موردنیاز تمرین کافی‌اند.

## ساختار سادهٔ کد

- **بخش API:** درخواست HTTP را می‌گیرد، عملیات مربوط را صدا می‌زند و نتیجه را به کاربر برمی‌گرداند.
- **بخش منطق کسب‌وکار:** بررسی می‌کند کاربر اجازهٔ انجام عملیات را دارد و وضعیت فعلی درخواست اجازهٔ آن تغییر را می‌دهد.
- **بخش ذخیره‌سازی:** اطلاعات درخواست‌ها را می‌خواند و تغییرات مجاز را ذخیره می‌کند.

مثال: وقتی کاربر درخواست تأیید می‌فرستد، API عملیات تأیید را صدا می‌زند. بخش منطق کسب‌وکار بررسی می‌کند که کاربر مجوز بررسی داشته باشد، ثبت‌کنندهٔ همان درخواست نباشد و درخواست در وضعیت PendingReview باشد. اگر همهٔ شرط‌ها برقرار باشند، وضعیت Approved ذخیره می‌شود. API نتیجه را برمی‌گرداند.

## جلوگیری از بازنویسی تغییرات هم‌زمان

هر درخواست تغییر یک شمارهٔ نسخه به نام `version` دارد که از ۱ شروع می‌شود. وقتی کاربر درخواست را می‌خواند، شمارهٔ نسخه را هم دریافت می‌کند و هنگام ویرایش یا تغییر وضعیت، همان شماره را می‌فرستد.

SQLite فقط وقتی تغییر را ذخیره می‌کند که شمارهٔ نسخهٔ ارسالی با نسخهٔ فعلی درخواست برابر باشد. ذخیرهٔ تغییر و افزایش شمارهٔ نسخه در یک عملیات انجام می‌شوند. اگر نسخهٔ ارسالی قدیمی باشد، سیستم عملیات را رد می‌کند، تغییر جدیدتر را حفظ می‌کند و از کاربر می‌خواهد درخواست را دوباره بخواند.

## شناسایی کاربر و بررسی مجوز

برای نسخهٔ تمرینی، چند کاربر با نقش‌های مشخص و توکن دسترسی آزمایشی آماده می‌کنیم. کاربر توکن را در هدر `Authorization: Bearer <token>` می‌فرستد. سرور توکن را اعتبارسنجی می‌کند و شناسهٔ کاربر را از آن به دست می‌آورد. شناسهٔ ثبت‌کننده و نقش کاربر از بدنهٔ درخواست پذیرفته نمی‌شوند.

نقش‌ها در SQLite نگهداری می‌شوند. برای هر عملیات، سرور نقش فعلی کاربر را از دیتابیس می‌خواند. اگر نقش Reviewer بعد از مشاهدهٔ درخواست لغو شده باشد، کاربر دیگر نمی‌تواند درخواست را تأیید کند یا برای اصلاح برگرداند.

Requester درخواست‌های خودش را می‌بیند. Reviewer درخواست‌های در وضعیت `PendingReview` را می‌بیند. کاربری که هر دو نقش را دارد، مجموع این دسترسی‌ها را دارد. برای تأیید یا بازگرداندن درخواست، Reviewer باید فردی غیر از ثبت‌کنندهٔ آن درخواست باشد.

مقدار اصلی توکن فقط در اختیار کاربر آزمایشی قرار می‌گیرد. در دیتابیس اثر انگشت توکن ذخیره می‌شود. توکن واقعی در کد، لاگ یا Repository ثبت نمی‌شود. برای این نسخه، صفحهٔ ورود و سرویس مدیریت حساب کاربری پیاده‌سازی نمی‌شوند.

## ذخیره‌سازی و تغییرات هم‌زمان

درخواست‌ها، کاربران، نقش‌ها و اطلاعات اعتبارسنجی توکن در SQLite ذخیره می‌شوند. پیش از اجرای API، اسکریپت آماده‌سازی جدول‌ها و داده‌های آزمایشی را ایجاد می‌کند.

برای ویرایش و تغییر وضعیت، بررسی نقش فعلی، مالکیت، وضعیت و نسخه و سپس ثبت تغییر در یک تراکنش انجام می‌شوند. دستور به‌روزرسانی فقط در صورتی ردیف را تغییر می‌دهد که شناسه و نسخهٔ فعلی با مقادیر مورد انتظار برابر باشند. در همان به‌روزرسانی، نسخه یک واحد افزایش می‌یابد.

اگر دو تغییر معتبر با نسخهٔ یکسان برسند، حداکثر یکی ذخیره می‌شود. تغییر دوم پس از بررسی نسخه، با خطای تعارض رد می‌شود. در تعارض نسخه، کاربر درخواست را دوباره می‌خواند و بعد دربارهٔ ارسال مجدد تصمیم می‌گیرد.

## قرارداد API

قرارداد نسخهٔ اول در `contracts/change-requests-api.md` ثبت می‌شود. پاسخِ ساخت، مشاهده، ویرایش و تغییر وضعیت، شمارهٔ نسخهٔ فعلی را برمی‌گرداند. فهرست و مشاهدهٔ تکی هر دو قواعد دسترسی ثبت‌شده در CL-02 را رعایت می‌کنند.

## طرح آزمون

آزمون‌های HTTP با دیتابیس آزمایشی اجرا می‌شوند. آزمون‌های حساس، هم پاسخ API و هم دادهٔ ذخیره‌شده را بررسی می‌کنند.

| سناریو                            | نیازمندی      | چیزی که بررسی می‌کنیم                                       |
| --------------------------------- | ------------- | ----------------------------------------------------------- |
| ثبت موفق درخواست                  | FR-01         | پاسخ 201 و ذخیرهٔ درخواست با وضعیت Draft و شناسهٔ ثبت‌کننده |
| ارسال پیش‌نویس                    | FR-02         | پاسخ 200 و ذخیرهٔ وضعیت PendingReview                       |
| تلاش برای تأیید درخواست خود       | FR-04         | پاسخ 403 و حفظ وضعیت PendingReview                          |
| تأیید توسط Reviewer مستقل         | FR-03 و FR-06 | پاسخ 200 و ذخیرهٔ وضعیت Approved                            |
| تلاش برای ویرایش درخواست تأییدشده | FR-05         | پاسخ 409 و حفظ محتوا و وضعیت Approved                       |
| ذخیره با نسخهٔ قدیمی              | FR-07         | پاسخ 409 و حفظ آخرین تغییر ذخیره‌شده                        |
| تلاش برای بازگرداندن درخواست خود  | FR-04 و CL-06 | پاسخ 403 و حفظ وضعیت PendingReview                          |
| اقدام پس از لغو نقش Reviewer      | FR-06 و CL-03 | پاسخ 403 و حفظ وضعیت PendingReview                          |

پس از پیاده‌سازی، فرمان‌های اجرا و نتیجهٔ واقعی آزمون‌ها در گزارش تحویل ثبت می‌شوند.
