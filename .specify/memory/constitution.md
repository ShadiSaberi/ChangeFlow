## Core Principles

### I. جداسازی مسئولیت‌ها

API درخواست را دریافت می‌کند، اجرای عملیات را به لایهٔ مربوط می‌سپارد و پاسخ را برمی‌گرداند. قواعد کسب‌وکار در Domain یا Application پیاده‌سازی می‌شوند.

برای مثال، بررسی اینکه ثبت‌کننده می‌تواند درخواست خودش را تأیید کند، در Domain یا Application انجام می‌شود. API نتیجهٔ این بررسی را به کاربر برمی‌گرداند.

### II. بررسی هویت، مجوز و وضعیت

پیش از هر عملیات تغییر وضعیت، سیستم باید هویت کاربر، مجوز فعلی او و مجاز بودن عملیات در وضعیت فعلی درخواست را بررسی کند. اگر یکی از این بررسی‌ها موفق نباشد، عملیات رد می‌شود و وضعیت درخواست تغییر نمی‌کند.

برای مثال، حتی اگر ثبت‌کننده نقش Reviewer هم داشته باشد، سیستم اجازه نمی‌دهد درخواست خودش را تأیید کند.

### III. جلوگیری از تداخل تغییرات

اگر درخواست از زمانی که کاربر آن را خوانده تغییر کرده باشد، سیستم باید عملیات مبتنی بر اطلاعات قدیمی را رد کند، تغییر جدیدتر را حفظ کند و به کاربر اطلاع دهد که درخواست را دوباره بخواند. عملیات هم‌زمان نباید درخواست را در وضعیت ناسازگار قرار دهند.

### IV. آزمون خودکار رفتارهای مهم

مسیرهای اصلی درخواست تغییر و قواعدی که جلوی عملیات غیرمجاز یا تداخل تغییرات را می‌گیرند، باید با آزمون خودکار پوشش داده شوند. در سناریوهای حساس، آزمون باید پاسخ API و وضعیت ذخیره‌شدهٔ درخواست را بررسی کند.

برای مثال، وقتی ثبت‌کننده تلاش می‌کند درخواست خودش را تأیید کند، آزمون باید نشان دهد که عملیات رد شده و وضعیت ذخیره‌شدهٔ درخواست همچنان PendingReview است.

### V. سادگی و توسعهٔ تدریجی

برای هر قابلیت، ساده‌ترین طراحی‌ای را انتخاب می‌کنیم که نیاز فعلی را برآورده کند و قابل نگهداری باشد. هر لایه یا ابزار جدید باید یک نیاز مشخص از نسخهٔ فعلی را برطرف کند. قابلیت‌هایی که در جلسات بعد تعریف می‌شوند، در همان زمان طراحی و پیاده‌سازی خواهند شد.

## محدودهٔ نسخهٔ اول

نسخهٔ اول ChangeFlow گردش ثبت، ارسال، بررسی، تأیید و بازگرداندن درخواست تغییر برای اصلاح را از طریق HTTP API ارائه می‌کند. ارائهٔ رابط کاربری برای تحویل این نسخه اختیاری است. قابلیت‌های AI، RAG، MCP و Multi-Agent خارج از محدودهٔ این نسخه هستند.

## بازبینی و شرایط تکمیل قابلیت

پیش از ادغام کد، تغییرات باید با مشخصات قابلیت و اصول این سند بررسی شوند. پروژه باید با موفقیت Build شود و آزمون‌های مرتبط اجرا شوند. دستورهای اجرا و نتیجهٔ واقعی آزمون‌ها ثبت می‌شوند.

اگر بازبینی نشان دهد که یکی از قواعد پروژه رعایت نشده یا یکی از معیارهای پذیرش هنوز بررسی نشده است، قابلیت تا رفع ایراد و تکمیل بررسی، آمادهٔ تحویل محسوب نمی‌شود.

## Governance

در بازبینی هر تغییر، رعایت اصول این سند بررسی می‌شود. اگر لازم باشد یکی از اصول تغییر کند، دلیل تغییر و اثر آن روی مستندات، کد و آزمون‌ها ثبت می‌شود. پس از تأیید تغییر، نسخه و تاریخ آخرین اصلاح سند به‌روزرسانی می‌شوند.
